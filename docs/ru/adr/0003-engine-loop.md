# ADR-0003: Планировщик кадров и цикл событий

## Статус
Принято

## Контекст
Движку TUI нужен единый владелец терминального ввода-вывода. Три
параллельных источника питают движок:

1. **Сырой ввод** из tty в raw-режиме — escape-последовательности,
   события мыши, focus-репорты.
2. **Уведомления об изменении размера** от ОС (SIGWINCH на Unix,
   console-события на Windows).
3. **Кадровые тики** от планировщика реального времени, которые
   запускают Diff → Render → Write.

Без явного планировщика путь рендера вызывается ad-hoc из обработчиков
ввода и жжёт CPU, либо блокируется на медленной записи и теряет ввод.

## Решение
Пакет `core/loop` владеет тремя горутинами движка:

- **Горутина ввода-вывода** читает сырые байты, прогоняет их через
  `internal/term.Parser` и отправляет типизированные события
  (`KeyEvent`/`MouseEvent`) в буферизированные каналы. Записи в каналы
  неблокирующие; переполненный ввод отбрасывает события, а не
  блокирует рендер.
- **Горутина планировщика** запускает `Flush` с частотой
  `time.Ticker` (60 Гц по умолчанию).
- **`Flush`** сериализует Diff, Render и единственную запись. Берёт
  мьютекс, чтобы внешние вызывающие абоненты и планировщик не
  конкурировали. После записи продвигает `BackBuf` → `FrontBuf`
  аллокационно-чистым `copy`.

`Stop()` идемпотентен и разбит на `signalStop()` (закрыть Quit,
остановить тикер) и `wg.Wait()`; горутина ввода-вывода использует
`signalStop()` на `ErrTTYLost`, потому что вызов `Stop()` изнутри
горутины, которую `wg` сам отслеживает, привёл бы к дедлоку.

Закрытый интерфейс `ioTerm` (только read/write поверхность) делает
цикл тестируемым без настоящего терминала.

## Обоснование

- **Детерминизм** — один бюджет кадра, одна запись на кадр,
  предсказуемая задержка ввода.
- **Нулевые аллокации** — каналы, буферы, differ и рендер
  предварительно выделены; горячий путь — чистая арифметика и
  `copy`.
- **Backpressure** — неблокирующие send не дают обратному давлению
  ввода голодить рендер.
- **Тестируемость** — интерфейс `ioTerm` позволяет тестам прогонять
  цикл целиком без форка настоящего tty.

## Последствия

- Drop-on-full ввод — единственный безопасный выбор под нагрузкой;
  приложения, не терпящие потерь, должны быстро дренировать
  `KeyEvents`/`MouseEvents`.
- `Flush` — единственный публичный метод, мутирующий состояние
  терминала; любой обходной путь должен повторить продвижение
  back-to-front.
- Resize пока не подключён к платформенному слою; подключение
  SIGWINCH отслеживается как последующая задача.
